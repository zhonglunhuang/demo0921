## 一、部署管線是壞的，而且不是你能修的

GitHub Actions 的 CD（`.github/workflows/deploy.yml`）需要 4 個 repo secrets：
`DEPLOY_SSH_HOST` / `DEPLOY_SSH_USER` / `DEPLOY_SSH_KEY` / `DEPLOY_APP_PATH`——
**至今未設**，所以每次 push stage 的自動部署都在「Setup SSH」步驟失敗。

- **不要**嘗試去「修」workflow 檔——檔案沒壞，缺的是 secrets，那只有使用者能在
  GitHub 設定（私鑰尤其不該經你手）。
- **不要**把 push 成功回報成部署成功。驗部署 = `gh run list --branch stage` 看結論
  ＋ stage 網址實際打 healthz。
- 使用者若問「為什麼 stage 沒更新」，答案九成是這個，先查 `gh run`，30 秒省你半小時。
- 替代路徑：在能 SSH 到主機的機器跑 `make stage`（本地部署，含健康閘門與回滾）。

## 二、這個框架的每條紀律都是傷疤，不是裝飾

你會覺得有些規則很煩：開場一定要簡報＋選入口（連使用者打「嗨」也是）、無票不開發、
PM 必問四件事。**它們都對應真實事故**：早期 agent 自行假設使用者角色與登入方式，
導致登入與權限被反覆重構（FRAMEWORK.md §3 v1.0.0）。

- 覺得規則不合理 → 走 framework 入口跟使用者討論修改（豁免票、留痕即可），
  **不要單方面「靈活變通」**。變通一次，制度就開始死。
- 票務閘門擋你 → 它在正常工作。開票，或請使用者決定是否 hotfix-override。
- 使用者本人明確要求跳過儀式時，照他說的做並提醒一句即可——制度約束的是你的自作主張，
  不是使用者的意志。

## 三、幾個環境事實，先知道省得撞牆

- 工作區 `Baojay-staging/` **不是** git repo；主專案在 `baojay/`（才是 repo）。
- 分支模型：`stage`（整合，日常都在這）→ `prod`（正式）；`develop` 已死不用，
  本地 `main` 已刪。從 stage 開 `feature/<票號>-<短題>`。
- 本機 runtime 是 **Colima**（不是 Docker Desktop）；PM demo 用 `make dev-lite`（5 容器），
  完整開發用 `make dev`（8 容器）；lite 模式 beat 排程不跑。
- auto-memory 在用（session 自動載入索引）：使用者給的偏好/糾正要寫進去（type: feedback），
  別讓同一句話講第三次。題外發現用 `spawn_task` 開背景任務 chip，不要順手修。
- 使用者慣用繁體中文；回報風格要人話、結論先行。

## 這套制度最可能的退化方式（與預防）

1. **膨脹到沒人讀**：每 session 都往檔案裡塞一點，兩個月後 250 行變 800 行，
   路由被跳過。→ 預防：`40-MAINTENANCE.md` §4 的尺寸觸發線是硬的，達標就發起精簡；
   你發現自己「沒讀就派工」，那就是已經開始退化的訊號，回頭補讀並檢查檔案是否過長。
2. **儀式化空轉**：把「派工」本身當成合規表演——為 5 行的 grep 開 subagent、
   模板填空填得很漂亮但驗收條件不可驗。→ 預防：`10` §2 的下場門檻是雙向的，
   低於門檻**就該自己做**；驗收條件寫完自問「這句能打 ✅/❌ 嗎」。
3. **驗收橡皮圖章**：fresh-context 驗收者退化成「看過，沒問題」。→ 預防：驗收回報
   必須逐條附證據（`30` T5 的格式），沒證據的 ✅ 視同未驗收，重派。
4. **規則打架沒人發現**：多處檔案各自演化出矛盾條款。→ 預防：規則只寫一處
   （單一來源），其他地方用路徑引用；改 harness 檔後跑 `40` §5 自檢清單。
