# 30 — 派工 prompt 模板

> 用法：複製對應模板 → 填 `<...>` 空格 → 作為 Agent 工具的 `prompt`。
> `【】`內是給你（指揮官）看的填寫指引，填完刪掉。三件套（目標動機/驗收/回報格式）
> 已內建在每個模板裡，**不要刪掉任何一節**。
> 通用鐵則：subagent 看不到本對話——路徑、票號、背景全部寫進 prompt，不要寫「如前所述」。

---

## T1 搜尋/定位（Explore；haiku=純定位、sonnet=需理解語意）

```
【目標與動機】
在 <目錄範圍，如 backend/> 找出 <要找什麼，如「維修單狀態機的定義與所有轉移點」>。
動機：<主任務一句話，如「BJ-000X 要加一個新狀態，需先知道現有轉移邏輯在哪」>。

【必查線索】
- 關鍵字：<詞1、詞2，含中英文與可能的命名變體>
- 可能位置：<猜測的路徑，沒有就寫「無，全範圍掃」>

【驗收條件】
- 找到：每個命中點給 檔案:行號 ＋ 一句話說明它是什麼。
- 找不到：列出已搜過的目錄與關鍵字（證明搜過），並給你認為最可能的原因。

【回報格式】
條列 ≤10 行，不貼程式碼原文（>3 行的內容只給 檔案:行號 讓主對話按需開）。
```

## T2 實作（general-purpose + isolation:"worktree"；預設 sonnet）

```
【目標與動機】
依票 tickets/<BJ-XXXX-xxx.md> 實作：<需求一句話>。
動機/背景：<誰用、解決什麼問題——從票裡抄過來，subagent 看不到票外討論>。

【範圍與邊界】
- 預期動的檔案：<清單或目錄；「大概在 backend/xxx/」也行>
- 明確不要動：<如「不動 migration 既有檔」「不改 API 對外格式」「不碰其他票的範圍」>
- 遵守 AGENTS.md（工程契約）；使用者可見功能要同步 Web+Mobile 與 docs/SPEC.md。

【驗收條件】
1. <可驗證條件1，如「admin 彙總頁每倉顯示總台數，除役不計」>
2. <條件2...>
3. `make <對應檢查，如 backend-check backend-test>` 全綠。

【回報格式】
- 變更摘要：動了哪些檔（檔案:行號級），每檔一句話為什麼。
- 驗收自查：逐條標 ✅/❌ 附證據（測試輸出貼關鍵行即可）。
- 殘留問題/假設：沒有就寫「無」。全文 ≤20 行；大 diff 留在 worktree 不要貼。
```

## T3 重構（general-purpose + worktree；sonnet，跨模組用 opus）

```
【目標與動機】
重構 <目標範圍>：<要改善什麼，如「XxxAdmin 三個類別重複的倉別過濾邏輯抽成 mixin」>。
動機：<為什麼值得，如「第 4 個 admin 要加同樣過濾，再複製就是第 4 份」>。

【行為保持契約（重構的定義）】
- 對外行為（API 回應、頁面呈現、CLI 輸出）不得改變。
- 重構前先跑 <測試指令> 記錄基線；重構後同一組測試必須同樣全綠。
- 測試不足以覆蓋被重構區域時：先補「鎖行為」的測試再動手；補不了就停下回報，不要裸改。

【驗收條件】
1. 基線測試前後皆綠（回報兩次輸出的關鍵行）。
2. <重構目標的可驗證形式，如「三處重複邏輯收斂為一處，重複行數 -X」>。
3. 無順手修改：diff 內不得出現與本重構無關的變更。

【回報格式】
同 T2。另附「行為保持證據」：基線與重構後的測試輸出對照。
```

## T4 研究（general-purpose；sonnet）

```
【目標與動機】
研究 <題目，如「Django admin 內做唯讀彙總頁的主流做法（proxy model vs 自訂 view）」>。
動機：<要支撐什麼決策>。

【範圍】
- 來源：<官方文件優先/本 repo 現有做法/網路搜尋，明確指定>
- 深度：<「比較 2-3 個方案的取捨」或「只要確認 X 是否可行」>
- 時效：注意資訊版本（本 repo：Django + django-unfold，版本以 pyproject 為準）。

【驗收條件】
- 每個結論附來源（URL 或 檔案:行號）；查不到的明標「未查證」，不編造。
- 有明確建議＋一句話理由，不是「都可以」。

【回報格式】
報告全文寫到 <路徑，如 cache/research/YYYY-MM-DD-題目.md>，
回主對話只給：路徑＋結論 3 行（建議方案/關鍵理由/主要風險）。
```

## T5 審查/驗收（general-purpose，fresh context；sonnet，高風險 opus）

```
【目標與動機】
以驗收者身分審查 <worktree 路徑或分支> 的變更是否滿足下列驗收條件。
你沒有參與實作，這正是你的價值：不要腦補實作者的意圖，只看實際產出。

【驗收條件】（逐條查證，不是看過就好）
1. <條件1>
2. <條件2>
...

【查證方式】
- 文件類：逐檔 read-back 對照條件。
- 程式碼：實際跑 <測試/檢查指令>，不是讀 code 覺得對就過。
- 【高風險加查】資安：硬編碼祕密、注入、權限繞過；有疑慮寧可誤報。

【回報格式】
- 逐條 ✅/❌ ＋ 證據（指令輸出關鍵行或 檔案:行號）。
- 總判定：通過 / 退回（退回必附：差在哪、建議的最小修法）。
- 任何一條 ❌ = 總判定退回。不要「大致沒問題」這種和稀泥結論。
```

## 常見錯誤（派工前自查 10 秒）

1. prompt 裡有「剛剛/上面提到的」→ subagent 看不到，改寫成自包含。
2. 驗收條件寫成「確保品質良好」→ 不可驗證，改寫成可打 ✅/❌ 的句子。
3. 忘了規定回報長度 → 準備收一篇 200 行的作文。
4. 實作票沒開 worktree → 主工作區被弄髒，驗收前先污染。
5. 讓實作者自己驗收 → 違反 `10` §6，重派 T5。
