# 20 — 判準手冊（判斷力外化）

> 讀者：任何等級的模型。每條判準都附正例／反例——對號入座，不要憑感覺。
> 「正例」= 該這樣做；「反例」= 常見的錯誤做法。

## 1. 何時該升級模型（而不是再試一次）

**判準**：失敗的原因是「理解不了」而非「資訊不夠」時升級。補資訊自己補，補智力要升級。

- 訊號：輸出邏輯自洽但答非所問；同樣的錯修不掉；對驗收條件的理解每輪漂移。
- 輪數上限與路徑照 `10-MODEL-DISPATCH.md` §5 執行，不重複。

✅ 正例：sonnet 兩輪都把「彙總頁不計除役機器」實作成「隱藏除役欄位」——對規格的理解錯位，
帶失敗軌跡升 opus。
❌ 反例：sonnet 因為「缺少某 model 欄位名」而失敗，就升 opus——這是資訊不夠，
派 Explore 查到欄位名再餵回 sonnet 就好，升級是浪費。

## 2. 何時算真的完成（Definition of Done）

**判準**：五條全過才能說「完成」。少一條就明說「做完了但缺 X」。

1. 驗收條件**逐條**有證據（測試輸出／read-back 結果／實跑截圖或回應）。
2. fresh-context 驗收通過（`10` §6，寫的人不驗收）。
3. `make check` 對應子集綠燈（改後端跑 backend-check/test；改前端跑 frontend-*；
   改 mobile 跑 mobile-check；只改 docs 可免）。
4. 留痕已同步：票況推進、`docs/SPEC.md` 更新（使用者可見功能）、
   `docs/FRAMEWORK.md`（框架變更）。
5. 回報無隱瞞：失敗的測試、跳過的步驟、已知的殘留問題都寫出來。

✅ 正例：「BJ-0004 完成：驗收 4/4 ✅（證據附後）、fresh 驗收過、backend-check 綠、
票標完成、SPEC 已同步。已知殘留：翻頁在 >50 倉時未測。」
❌ 反例：「code 寫完了，應該可以用」——沒有一條有證據，這叫「寫完」不叫「完成」。
❌ 反例（本 repo 真實案例）：push 成功就回報「已部署 stage」——CD 其實一直失敗
（SSH secrets 未設），要查 `gh run list` 看結論才算數。

## 3. 何時該停下來問使用者

**判準**：滿足任一條就停。問一次的成本 << 做錯一次的成本。

1. **不可逆或對外**：push、merge 到 stage/prod、部署、刪資料、動 secrets、對外發送。
   本次對話已明確授權的**那個具體動作**除外——授權不外溢。
2. **規格有兩種合理解讀，且做出來的東西會不同**（UI 長相、API 行為、權限範圍）。
3. **票務閘門或權限被擋**：回報＋建議下一步，不嘗試繞過。
4. **預算失控**：預估總嘗試要 >5 輪、或 diff 規模遠超任務描述（小任務長出 >20 檔變更）。
5. **發現使用者的前提有誤**（他以為 A 存在但已被移除）：先對齊事實再繼續。

✅ 正例：使用者說「幫我推上 stage」→ 推 stage 可以；但發現 prod 也落後想「順手」推 → 停，
prod 沒被授權。
❌ 反例：「加個匯出功能」沒說格式，自行假設 Excel 做完整套——本 repo 曾因假設角色
反覆重構登入（FRAMEWORK v1.0.0 決策），假設規格 = 重蹈覆轍。
❌ 反例（過度問）：內部變數命名、log 文案、測試檔放哪——有專案慣例可循的事不問，
照 AGENTS.md 與周邊程式碼的慣例做。

## 4. 方向錯了的訊號（該換路，而不是重試）

**判準**：出現任一訊號，停止當前路線，回到上一個決策點重新選路；換路前先寫下
「原路線為什麼不通」（一行即可），避免下一輪又走回去。

1. **蹺蹺板**：修 A 壞 B、修 B 又壞 A ——抽象層級錯了，問題在共同的上游。
2. **特例堆疊**：同一段邏輯第 3 個 if/特判出現——模型選錯或資料形狀理解錯。
3. **驗收漂移**：為了通過驗收而改驗收條件——立即停，這是自欺。
4. **同錯重現**：同一個錯誤訊息在「修好」之後第二次出現——第一次的診斷就是錯的。
5. **規模爆炸**：診斷「小 bug」但修法要動 >5 個模組——大概率在錯的地方修。

✅ 正例：修 admin 彙總頁數字不對，兩次都在模板層補救無效 → 停，回頭查 queryset，
發現彙總邏輯在 model manager 就錯了——換路修上游，模板層兩個補丁全撤。
❌ 反例：同一個 migration 衝突「解掉」三次又出現，繼續在衝突檔上手動改——
應該停下來查是不是兩條分支各自生了同號 migration（結構問題，不是檔案問題）。

## 5. 品質底線怎麼驗（按變更類型）

| 變更類型 | 最低驗證（缺一即未達標） |
|----------|--------------------------|
| 後端 | `make backend-check` + `make backend-test`；動 model 加跑 `make dev-makemigrations` 確認無未生成 migration |
| 前端 | `make frontend-lint` + `frontend-test` + `frontend-build`（build 過才算，lint 過不夠） |
| Mobile | `make mobile-check` |
| 使用者可見功能 | 上列對應項＋Web/Mobile 兩邊都檢查＋SPEC 同步（AGENTS.md 契約） |
| 文件/制度檔 | fresh-context read-back：讀的人只拿「這份文件該回答什麼問題」清單，答不出=不過 |
| 部署/infra | 終態驗證：healthz 綠、`gh run` 結論 success、目標網址實際看到新版 |
| 框架（skills/hooks/契約） | framework SKILL 的一致性自檢清單逐項過＋FRAMEWORK.md 版號與紀錄 |

## 6. Harness 的極限（誠實條款——這些補不了，別假裝能）

- **模糊題與品味判斷**（文案語氣、UX 取捨、「好看」）：拆解與多樣本評審只能逼近。
  處理順序：找專案既有先例模仿 → 出 2-3 個方案附取捨讓使用者選 → 明說「這題需要人的品味」。
  **不要**由單一弱模型硬拍板然後當成定案。
- **領域知識空洞**（本地法規、行業慣例、案主的商業邏輯）：查不到就標註「未查證」，
  寧可留白也不要編造。編造的成本是使用者的信任。
- **長鏈路因果推理**（「這個改動三個月後會不會咬人」）：弱模型做不可靠。寫下顧慮、
  標記為風險，交給使用者或 opus 級的專門審查，不要默默吞掉。
