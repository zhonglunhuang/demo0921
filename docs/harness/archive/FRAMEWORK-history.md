# FRAMEWORK 決策紀錄前史（源專案 baojay，v1.0.0–v3.1.0）

> 本框架模板萃取自一個真實外包專案。這份是模板化（v4.0.0）前的完整決策表，
> 原樣保留供翻舊帳；dispatch.md 的案例編號（C1–C4）所引用的決策列也在這裡。
> **不要**把本檔內容回填到 `docs/FRAMEWORK.md` 正文。

| 版號 | 日期 | 決策（改了什麼） | 原因（為什麼） |
|------|------|------|------|
| v3.1.0 | 2026-07-04 | **新增「推分支前先同步遠端」機制化閘門** `scripts/git-sync-gate-hook.sh`（PreToolUse matcher: Bash）：`git push` 前 fetch，本地落後上游就擋下（exit 2），要求先 `git pull --rebase origin <分支>` 整合再推；只擋不自動 rebase（避免 hook 內卡 rebase 中途），fetch 失敗放行（不因網路波動擋工作）。MINOR：新增機制化能力 | 多個 session 平行開發（源專案 stage 同時被多方推進），直接 push 易衝突或覆蓋他人 commit；把「push 前先拉遠端」從自律升級為 hook 強制，和「無票不開發」同一套機制 |
| v3.0.0 | 2026-07-03 | **制度檔收斂**（依使用者收斂指令）：v2.2.0 的七檔重構為硬上限四檔——`dispatch.md`（≤60 行主檔，含門檻/派工表/升降級/驗證/DoD/問人/換路判準）、`templates/`（5 份各 ≤25 行）、`sensors-backlog.md`（≤30 行，可機制化規則清單）、`maintenance.md`（≤25 行）。**每條規則補來歷**：[C1] push成功但CD失敗、[C2] 假設角色致重構、[C3] log-5 誤判、[C4] A/B 實測；無案例者標 [猜]（2026-10-01 到期未驗證即提議刪）。舊七檔整份移 `archive/`（不刪）。MAJOR：資料夾契約變更 | 使用者要求收斂瘦身＋補來歷：規則要嘛有真實案例撐腰、要嘛標猜的並限期驗證，防制度膨脹成沒人讀的教條；能自動擋的規則列入機制化 backlog 而非留文字 |
| v2.2.0 | 2026-07-03 | **建立 Agent 制度檔 `docs/harness/`**（由一次性強模型 session 外化判斷力，供之後較弱模型沿用）：診斷三大失效模式（主對話下場大量讀取、自驗偏誤＋動作成功≠結果成功、重試螺旋與範圍蔓延）、模型調度表、升降級路徑、驗證不自驗、判準正反例、五份派工模板、維護協議。兩層 CLAUDE.md 重寫為精簡路由 | 使用者環境將長期由較小模型運作，要求把強模型的判斷力轉成弱模型可執行的制度（具體門檻、判準、正反例），並降低 CLAUDE.md 的 token 重複 |
| v2.1.1 | 2026-07-03 | **新增模板身份收斂規則**：AGENTS.md 要求 Agent 主動檢查並同步模板殘留的專案名稱、網域、DB 名稱、env examples、app identity 等 | 源專案本身源自通用模板，容易在部署或改名時留下模板殘留造成 runtime mismatch；把規則寫進工程契約，讓 Agent 看到殘留主動提修正 |
| v2.1.0 | 2026-07-03 | **PM 本機起機器改用輕量版**（`make dev-lite`：精簡容器＋自動管理 Colima） | PM/案主只是要點畫面、demo、驗收，不需要完整容器陣列；用更輕的 runtime 省資源、起得快 |
| v2.0.0 | 2026-07-02 | **PM 入口升級為「非工程師開發代理」**：推翻原「PM 不寫程式」契約——PM 也能實際開發並出貨，由 agent 主導、白話回報；dev 則是工程師參與技術/資安檢查。兩者**能力相同、都先開票、共用出貨流程**，差在使用者是誰與呈現 | 使用者要讓不懂 code 的 PM 也能直接把功能做出來、push；但保留「先確認角色與目的再開建」「無票不開發」不變（gate 不拆），避免回到假設角色反覆重構的老坑 |
| v2.0.0 | 2026-07-03 | **新增「分支與出貨流程」契約**（AGENTS.md），對齊 CONTRIBUTING.md「分支即環境」：開發從 **`stage`** 開 `feature/*`，可實機測試時**先問使用者**→ merge 回 `stage` 做真裝置驗收 | 使用者要一條清楚的「開新 feature → 實機測試 → 進 stage」出貨路徑，且部署類對外動作一律先經人工確認 |
| v1.5.0 | 2026-07-02 | **框架版號制度**：FRAMEWORK.md 檔頭加「框架版本」單一事實來源、決策紀錄加版號欄並回填歷史、定義 semver bump 規則、framework SKILL 落地步驟強制 bump、`agent-status.sh` 簡報顯示版號 | 使用者要求框架可版本化、每次修改都有版號與原因可追溯；把「留痕」從慣例升級為帶版號的制度 |
| v1.4.0 | 2026-07-02 | **「無票不開發」機制化**：PreToolUse hook（`scripts/ticket-gate-hook.sh`），無「待開發/開發中」票時擋下產品程式碼的檔案寫入；救火以 `cache/hotfix-override` 豁免（使用者同意後），事後補票 | prompt 層紀律可能失守；最重要的規則值得用 harness 最硬的原語（hook 真攔截）保護 |
| v1.4.0 | 2026-07-02 | 新增**票務一致性 lint**（`scripts/ticket-lint.sh`，掛入 `make check`）：驗 frontmatter 格式、id 不重複、完成票須有 spec 欄位、spec 指向存在的檔案 | 一致性自檢交給 CI，漂移直接紅燈，不靠人記自檢清單 |
| v1.4.0 | 2026-07-02 | 工作區 settings 加入唯讀 MCP 權限允許清單 | 高頻唯讀工具不需逐次確認；程式碼執行類依安全原則刻意不放行 |
| v1.4.0 | 2026-07-02 | **強化入口簡報**（`scripts/agent-status.sh`）：修正 SPEC 統計誤計圖例表的 bug、只掃「功能狀態總覽」區段；新增未提交檔名摘要、⏳ 標題清單、最近變更、ticket-lint 結果、hotfix-override 閘門警示 | 簡報是每個入口的第一件事，正確與可行動性最重要；讓角色零額外讀檔就能點出待決事項與閘門風險 |
| v1.3.0 | 2026-07-02 | 啟用**背景 subagent**：長調查 / demo 素材 / 依票實作（隔離 worktree）可背景執行；進行中每回合開頭回報一行狀態，完成自動彙報；實作由主對話驗收後合回 | 長任務不該卡住與使用者的對話；harness 無常駐計時，「定期觀測」以完成自動通知＋每回合狀態查核實作（誠實映射 harness 能力） |
| v1.2.0 | 2026-07-02 | 開場改為**無例外攔停**：任何第一句話（含明確指定任務）都先完整簡報 + AskUserQuestion 入口選項；並掛 **SessionStart hook** 注入開場規則與即時狀態 | 純指令檔依賴載入時機與模型自覺，曾發生開場未觸發；hook 由 harness 於每個新 session 強制執行，且注入狀態省一次指令往返 |
| v1.2.0 | 2026-07-02 | 簡報改用單一指令 `scripts/agent-status.sh`（<1.5s），並加入權限白名單；切換入口不重新蒐集狀態 | 入口切換太慢：原本多次 git/健康檢查呼叫＋權限確認等待；收斂為一次呼叫、免確認 |
| v1.1.0 | 2026-07-02 | 新增 **framework 入口**；框架變更**豁免票**但必須寫入決策紀錄 | 框架自身的演進需要歸屬入口與留痕；用票管框架太重，用決策紀錄保住「為什麼」 |
| v1.0.0 | 2026-07-02 | 三角色入口（team-leader / pm / dev）以 **skill** 實作，不用 subagent | 入口需要與使用者來回互動；subagent 獨立 context 跑完才回報，不適合引導對話 |
| v1.0.0 | 2026-07-02 | team-leader 於**每個新 session 自動觸發**（寫進 CLAUDE.md） | 使用者不需記指令；已指定任務時壓縮簡報避免擋路 |
| v1.0.0 | 2026-07-02 | **每個入口進入時都先回報專案現況**（不只 team-leader）；已簡報過改差異更新 | 使用者直接跳入 /pm、/dev 時也要有完整脈絡；差異更新避免同對話重複轟炸 |
| v1.0.0 | 2026-07-02 | **無票不開發（嚴格）**；PM 開票前必問「角色 / 目的 / 驗收 / 邊界」 | 源專案曾因 agent 自行假設角色與情境導致登入與權限被反覆重構（→ dispatch.md 案例 C2） |
| v1.0.0 | 2026-07-02 | 票採**簡單三態**（待開發→開發中→完成） | 單人/小團隊維護成本低；多人協作再演進為五態 |
| v1.0.0 | 2026-07-02 | `tickets/` 進 git、`cache/` 不進 git | 票是開發依據需要版控與追溯；討論過程屬戰時狀態，正式結論一律落到票與 SPEC |
