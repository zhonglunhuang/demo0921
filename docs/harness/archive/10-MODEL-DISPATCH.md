# 10 — 模型調度守則（指揮官手冊）

> 讀者：主對話的模型，不論你是 Haiku、Sonnet 或 Opus。
> 原則一句話：**主對話是指揮官，負責判斷與整合；體力活派出去，只讓結論進 context。**

## 1. 本環境實際可用的旋鈕（查證過，不要憑印象）

- `Agent` 工具：`subagent_type` 可選 `general-purpose`（全工具）、`Explore`（唯讀搜索）、
  `Plan`（唯讀規劃）、`claude`（泛用）、`claude-code-guide`（查 Claude Code/API 文件）。
  `model` 參數可選 `haiku` / `sonnet` / `opus` / `fable`；省略則繼承主對話模型。
- `run_in_background: true` 可背景執行；完成會自動通知，**不要輪詢**。
- `isolation: "worktree"` 給 subagent 獨立 git worktree（實作票用這個，避免弄髒主工作區）。
- **沒有 effort 參數**——subagent 的「用力程度」只能靠任務範圍收窄與驗收條件控制。
  主對話自身靠 `/model` 切換；`/fast` 只影響 Opus 系列輸出速度，不降模型。
- `fable` 平常**不可用**（一次性）；調度表以 opus 為天花板。若真的指定 fable 而呼叫失敗，
  改用 opus，不要重試。

## 2. 下場門檻（主對話什麼時候可以自己動手）

主對話**可以**自己做（低於門檻就別派工，派工本身也有成本）：

- 讀 **≤2 個已知路徑**的檔案，且合計 **≤300 行**（會用 offset/limit 就只讀需要的區段）。
- 單一次 grep/glob，pattern 明確、預期命中位置心裡有數。
- 編輯 **≤3 個檔案**，且都已在 context 內讀過。
- 跑單一驗證指令（make check 子集、單一測試檔）。

超過門檻 → **派工**，對照下表。判斷猶豫時：問自己「這個產出的**原文**需要留在主對話嗎？」
只需要結論就派工。

| 情境 | 派給 | model |
|------|------|-------|
| 找檔案/找定義/「這功能在哪實作」 | Explore | haiku（純定位）/ sonnet（要理解語意才找得到） |
| 大範圍現況調查（掃多目錄、比對命名慣例） | Explore | sonnet |
| 架構規劃、實作前的方案設計 | Plan | opus |
| 有票有明確 spec 的實作 | general-purpose + worktree | sonnet |
| 機械批次修改（模式已定、重複套用） | general-purpose | haiku |
| 難 bug／資安敏感／跨模組重構 | general-purpose | opus |
| 網路研究、文件彙整 | general-purpose | sonnet |
| 驗收/審查（見 §6） | general-purpose（fresh） | sonnet；高風險 opus |

成本檔位=平衡：**sonnet 是預設工作馬**；opus 保留給判斷題；haiku 只做「答案已知、
只是量大」的事。不確定選哪個 → 選 sonnet。

## 3. 派工三件套（缺一不派）

每個派工 prompt 必含三件事（模板見 `30-DELEGATION-TEMPLATES.md`，直接填空）：

1. **目標與動機**：要什麼＋為什麼要（動機讓 subagent 在邊界情況做對取捨）。
2. **驗收條件**：可驗證的句子。「找到 X 並給出檔案:行號」可驗；「好好調查」不可驗。
3. **回報格式**：規定輸出形狀與長度上限，否則 subagent 會倒一整篇進主對話。

另外必記：subagent **中途不能提問**，prompt 必須自包含（背景、路徑、術語都寫進去）；
它也看不到本對話，「如上所述」「剛剛那個檔」是無效指涉。

## 4. 回報合約（subagent 端規則，寫進派工 prompt）

- 回報 = **結論 + 檔案:行號 + 驗證證據**，條列 ≤15 行。
- 長產物（報告、大 diff、log）**寫成檔案傳路徑**：調查報告放 scratchpad 或 `cache/`，
  程式碼直接改在 worktree。不要貼 >30 行的原文回主對話。
- 找不到／做不到就直說，並列出「已排除了什麼」（證明找過），**不要編造**。

## 5. 升降級路徑（防重試螺旋）

「一輪」= 一次派工＋一次驗收失敗。**同一子任務**：

- **haiku 失敗 1 輪** → 直接升 sonnet（haiku 不給第二次，它的失敗通常是能力不足非運氣）。
- **sonnet 失敗 2 輪** → 升 opus，且 prompt 必附**完整失敗軌跡**：原任務、兩次的輸出、
  驗收差距在哪。沒有軌跡的升級 = 讓 opus 重新踩一遍同樣的坑。
- **opus 失敗 2 輪** → 停。向使用者報告：試了什麼、卡在哪、三個選項（換方法／放寬驗收／
  人工介入）。**沒有第三輪**——連 opus 帶著失敗軌跡都解不掉的，繼續燒 token 不會更好。
- **降級**：opus 解出模式後，把「模式說明＋一個完整範例」寫成批次任務派 haiku/sonnet
  套用到其餘位置。判斷力貴、套用便宜，別讓 opus 做完全部。
- 微調 prompt 再派同模型 = 算重試，計入輪數。換模型 = 升級，輪數歸零重計。

## 6. 驗證不自驗（鐵則）

**寫的人不驗收。** 驗收一律派 fresh-context subagent（沒看過實作過程、只拿驗收條件）。
理由：實作者的盲點會原樣帶進自驗；fresh context 才會踩到「只有新人會踩」的坑。

| 產物 | 驗法 |
|------|------|
| 文件/設定檔 | read-back：驗收者逐檔開來讀，對照驗收清單逐條回報過/不過 |
| 程式碼 | 跑測試或實跑：`make check` 對應子集、`run-checks` skill、preview 實際點 |
| 對外動作 | 驗**終態**不驗動作：push 後查 `gh run` 結論、部署後打 healthz、寫檔後 read-back |
| 高風險判斷（資安/金流/權限/資料刪改） | **第二意見**：兩個獨立 agent 各自給結論，或 opus 審 sonnet 的產出；兩者衝突 → 升使用者 |

驗收者回報格式：逐條驗收條件標 ✅/❌ ＋ 證據（指令輸出、檔案:行號）；任何 ❌ 都算整體未過。

## 7. 背景執行紀律

- 預估 >2 分鐘或不需互動的派工 → `run_in_background: true`，主對話繼續服務使用者。
- 使用者每次來訊，回應開頭用一行回報背景任務狀態（進行中/完成/卡住）。
- 完成通知到了才處理結果；**不要**為了等 subagent 而空轉輪詢。
- 同時進行的背景任務 ≤3 個；more ≠ faster，驗收是瓶頸。
