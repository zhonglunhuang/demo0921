# 40 — 制度檔維護協議

> 讀者：未來想更新 `docs/harness/` 任何檔案的模型。
> 大原則：**這些檔是框架的一部分**——變更豁免功能票，但走 framework 入口紀律：
> 改前備份、改後在 `docs/FRAMEWORK.md` bump 版號＋補決策紀錄。

## 1. 可以自行改（不用問使用者）

| 動作 | 條件 |
|------|------|
| 在 `20-JUDGMENT.md` 附錄 LESSONS **追加**一列 | 格式照表頭（日期/情境/教訓/是否已轉正式規則）；只加不改舊列 |
| 修正**已失效的事實**（路徑改了、指令改名、工具消失） | 必附證據（實際跑過/查過的輸出）；改的是事實陳述，不是規則本身 |
| 修錯字、斷鏈、格式 | 不改語意 |

以上仍要：改前 `cp` 備份到 `cache/backups/<YYYYMMDD>/`、改後 FRAMEWORK.md 留痕
（LESSONS 追加與錯字可累積到當次 session 結束一起記一列，PATCH 級）。

## 2. 動之前必須先問使用者

- **改或刪任何既有規則**（門檻數字、升降級輪數、模型調度表、DoD 條目、模板結構）。
- 改兩層 CLAUDE.md 的路由結構、改 hooks（session-start / ticket-gate）。
- 精簡/合併/重排檔案（見 §4）。
- 新增一整個新制度檔。

問法：一句話說明「想改什麼、為什麼、改了之後行為差異」，給使用者可選項。

## 3. 踩坑教訓怎麼寫回（每次事故後做）

1. 落點：`20-JUDGMENT.md` 附錄 LESSONS 表，**append-only**。
2. 格式：`| 日期 | 情境（一句話，具體到可重認）| 教訓（下次怎麼做）| 是否已轉正式規則 |`
3. 判斷要不要「轉正式規則」：同類教訓在 LESSONS 出現**第 2 次** → 該升格為正文規則了
   （這屬 §2，要先問使用者）。第 1 次先留在表裡觀察。
4. 寫「情境」時足夠具體：❌「git 操作出錯」→ ✅「fetch 後 log -5 沒看到自己 commit
   就誤判被強推」。太抽象的教訓下次認不出來，等於沒寫。

## 4. 精簡時機與做法（防膨脹）

- **觸發條件**（任一達標就該精簡）：LESSONS >20 列；任一制度檔 >250 行；
  README 索引與實際檔案不符。
- **做法**：先問使用者（§2）→ 備份整個 `docs/harness/` 到 `cache/backups/<日期>/` →
  合併重複、把已升格的 LESSONS 從表中標記（不刪列，改註「已入 §X」）、刪已失效內容 →
  fresh-context read-back 驗證（拿 README 的「什麼時候讀」清單當驗收）→
  FRAMEWORK.md 留痕（MINOR）。
- **禁止**：未備份就重寫；把同一規則貼到多個檔案（單一來源，其他處用路徑引用）；
  為了精簡而刪掉正反例（例子是弱模型唯一的錨，寧長勿刪）。

## 5. 一致性自檢（改完 harness 檔後過一遍）

- [ ] README.md 索引表與實際檔案一致（檔名、用途、狀態）。
- [ ] 兩層 CLAUDE.md 路由指到的檔案都存在。
- [ ] 檔案間互相引用的章節號還對（如 `10 §6`、`20 §2`）。
- [ ] FRAMEWORK.md 版號已 bump、決策紀錄已補列。
- [ ] 備份已落在 `cache/backups/`。
