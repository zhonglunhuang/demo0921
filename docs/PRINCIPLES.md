# 生產原則（上線前必須想到的事）

> 這份是**鐵則清單**，給 AI Agent 與工程師在「長新功能」時逐條檢查。
> VibeCoding 最常見的坑不是「做不出來」，而是做出來「能 demo、但一上線就出事」：
> 沒想到並發、一致性、資安、可維護、可運維。**功能能跑 ≠ 可以上線。**
>
> 用法：每加一個功能，對照下面每一節問自己一次。AGENTS.md 的「生產鐵則」是摘要，這裡是「為什麼」與「怎麼做」。
> 本檔刻意 stack 無關；各節的落地做法（用哪個 ORM API、哪個框架的中介層）由專案技術棧決定，
> 可由 framework 入口把 stack 專屬範例補進對應小節。

---

## 1. 併發與資料一致性（最容易被忽略，後果最嚴重）

> 單人點一下沒事；100 個人同時點、或同一個人手殘點兩下，資料就壞了。

- **讀-改-寫一定要鎖或用原子運算。** 任何「先讀出目前值 → 算 → 寫回」的操作（扣庫存、加餘額、改狀態），
  在並發下會 race。兩種正解：數值增減用資料庫端原子運算；需要先讀值再決策就在交易內鎖列（select for update）。
- **金錢 / 庫存 / 計數操作一律包在資料庫交易。** 多張表的寫入要嘛全成功、要嘛全回滾，不能寫一半。
- **有副作用的操作必須 idempotent（可安全重試）。** 使用者會雙擊、網路會逾時重送、背景任務會重跑。
  對「建立型 / 扣款型」操作，接受客戶端帶的 **Idempotency-Key**，用它去重：同一把 key 只成功一次，
  重送回傳同一筆結果。
- **不要在資料庫交易裡呼叫外部 API。** 交易會一直握著鎖/連線，外部一慢就拖垮全部。
  交易內只寫 DB，提交後再用背景任務打外部（必要時用 outbox pattern）。
- **Webhook / 金流 callback**：先驗簽章 → 快速回 200 → 真正處理丟背景，且處理要 idempotent（對方會重送）。

## 2. 效能（隨資料量成長才會爆，demo 時看不出來）

- **列表端點必防 N+1**：有關聯就預先載入。一個列表頁打出 100 條 SQL 是預設會發生的事，不是意外。
- **列表端點一律分頁**。永遠不要回傳無上限的查詢結果。
- **常用來 filter / order 的欄位要加索引**（含複合索引）。
- **大量資料掃描**用串流/迭代器、只取需要的欄位，別把整批資料拉進記憶體。
- **>1 秒或打外部 I/O 的工作丟背景任務**：傳 ID 不傳物件、idempotent、設重試與逾時上限。

## 3. 資安（被打一次就出事）

- **權威欄位一律後端決定**：owner、價格、角色、狀態——不信任前端傳來的值。
- **資料隔離**：屬於使用者的資料一定以登入者過濾，避免越權讀寫。
- **認證端點限流**（登入、OTP、重設密碼），防暴力嘗試。
- **祕密走環境變數**，程式碼與版控裡不出現；log 不記 PII 與憑證。
- **輸入驗證在後端做**，前端驗證只是 UX。

## 4. 可演進（今天的方便是明天的遷移地獄）

- **API 版本化**（如 `/api/v1/`）、統一錯誤格式。
- **資料庫遷移用 expand/contract**：可空 → 回填 → 加約束；不可在一次部署做破壞性變更。
- **狀態機顯式化**：狀態欄位的合法轉移寫成規則，不散落在各處 if。

## 5. 可運維（出事時你要能知道、能救）

- **健康檢查端點**：涵蓋 DB / 快取 / 佇列等關鍵依賴，部署閘門靠它判斷。
- **部署要有回滾路徑**；部署前自動備份資料庫。
- **錯誤要進 log 並可追**（含 request id / 使用者 id），但不記敏感資料。
