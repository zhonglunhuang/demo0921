# 繁中 UX Writing

本 repo 的 UI 文字讀者是**非工程師**（終端使用者用 App／前台、行政營運用後台）。文字要好懂、精簡、中性，並且**全站用語一致**。以母語者的直覺寫，不是把英文翻成中文。

> **套用即揭露**：實作觸及 UI 文案時，要透過 Skill 工具實際啟動本 skill（工作過程會顯示「Launching skill: ux-writing」），讓使用者看得到文案有經過 ux-writing——不要只在心裡默默套用原則。

## 核心心法（排序＝優先級）

1. **一致性優先**——同一概念全站只用一個詞（見〈術語表〉）。寧可犧牲單句花俏，也要全站統一；不要只顧一個畫面的通順而自創同義詞。
2. **講事情，不講動作**——寫使用者得到什麼、要做什麼，不描述系統在做什麼。
3. **能砍就砍**——每個字都問「拿掉會不會看不懂」，不會就拿掉。按鈕控制在 2–4 字。
4. **中性語氣**——不用語尾助詞（囉／吧／喔）、不假客氣（歡迎／親愛的／請您／感謝您的耐心），也不用公文腔（予以／加以／敬請／務必／進行⋯⋯的動作）。給指示時用「請＋動詞」，但不加「您」。
5. **錯誤要給出路**——說哪裡錯、怎麼辦；而且同類錯誤全站用同一句。
6. **白話，但不是口語**——好懂與專業要同時成立。描述式的口語（「那個時段接不了」）
   讀起來像旁白；換成精準的短詞（「無法支援」）一樣好懂，而且更短、更乾淨。
   判準：**唸出來像不像一個專業的人在報告狀況**。狀態與系統訊息尤其要拿捏這個平衡。
7. **系統自己做的事，成功也要說一聲**——判準不是「成功要不要報」，而是
   **這件事是不是使用者自己動手做的**。他自己按的按鈕，畫面變了就知道；
   系統自動做的（自動指派、自動改派、自動關閉某個設定），不說他永遠不會知道。

## 術語表（一致性骨幹 · 由專案自己累積）

寫任何文字前先查這張表。**表由專案的實際定案累積**：每次與案主／團隊定下一個詞
（或改掉一個詞），就補一列並回寫所有用到的畫面；表裡沒有的新概念，先把決定的詞
加進表、再用，不要臨場造同義詞。下面兩列是格式示範（換成你們的定案後刪除）：

| 概念 | 統一用語 | 不要再出現 | 出處 |
|---|---|---|---|
| （示範）管理端角色 | 行政 | 使用者、管理員、工作人員 | 定案的票號或日期 |
| （示範）刪除按鈕 | 刪除此資料 | 刪除 XX | 定案的票號或日期 |

**共用字串（唯一版本，不要各處重寫）：** 密碼規則提示、停用帳號說明這類
會出現在多個畫面的句子，收斂成一句、記在這裡。

## 一致性規則

1. **一個概念一個詞**：先查術語表；沒有的新詞，加進表再用。
2. **錯誤訊息集中**：同類錯誤（網路、格式、權限、找不到）全站共用同一句，建議收在共用常數，不要每個畫面各寫一句。
3. **改詞要全站改**：動術語表任一詞，要同時掃所有介面（App／前台／後台）與 `docs/SPEC.md` 一起改。
4. **對照 SPEC**：用語有疑義時，以 `docs/SPEC.md`（單一事實來源）＋本術語表為準。
5. **同類的人或物並存時，名字前面要冠角色**：一個畫面同時有兩個以上同類的對象
   （例如「客戶欲指定業務」與「指派業務」）時，訊息只給名字，讀者得自己回想那是誰。
   訊息要冠上角色（「指定人選王小明」「原指派陳大同」），不要只寫名字。
6. **狀態要用畫面上的那個詞，而且同一個結果只准有一種說法**：訊息裡的狀態名稱
   必須與畫面標籤同字（畫面寫「未派工」就不要在訊息裡自創「未派工行程」），
   也不要用不同動詞描述同一個結果（「先進未派工」「已退回未派工」→ 一律「為未派工狀態」）。
   用動詞敘述是在**替系統講故事**，使用者要的是**現在是什麼狀態**。

## 標點與排版（務必遵守）

1. **標點一律全形**——繁體中文的標點必須用全形：`，。、；：？！「」（）〈〉`。不要用半形 `,.:;?!()` 混在中文裡。
2. **句號看長度**——短文字（只有幾個字，或一兩句話：按鈕、標題、標籤、空狀態、提示）結尾**不加句號**；一整段、比較長、有好幾行的說明文字，結尾**要加句號**。
3. **盤古之白**——漢字與半形英文／數字／符號之間加一個半形空格，劈開全形與半形（如 `剩 3 筆`、`iOS 版`、`iOS 14 以上`、`8 個字`）。
   - **例外**：緊鄰標點時不加空格（標點本身已隔開），例如 `（選填）`、`「iOS」`、`版本 2.0，請更新`（`2.0` 後直接接全形逗號）。
   - 同為半形的連續 token 內部不拆，例如 `NT$500`、`API`。
4. **斷行不斷詞**——窄版手機上，「今天截止」不要斷成「今天截／止」。
5. **數字與單位不分家**——`3 天`、`NT$500` 儘量不落在行尾被拆開。
6. **場合語氣**——App／前台（終端使用者）可稍口語但保持中性；後台（行政營運）更精簡專業。

## 逐句範例庫（before → after）

**按鈕**

- 確認送出訂單 → 送出訂單
- 立即進行預約 → 預約
- 取消並返回上一頁 → 取消
- 儲存並套用變更 → 儲存

**標題／空狀態**

- 目前尚未有任何預約紀錄 → 還沒有預約
- 您的班表目前是空的 → 這期還沒排班
- 查無符合條件的客戶資料 → 找不到符合的客戶
- 載入中，請稍候⋯ → 載入中⋯

**錯誤訊息（同類全站共用同一句）**

- 您所輸入的手機號碼格式不正確 → 手機號碼格式不對，請再確認
- 系統發生未預期之錯誤，請稍後再試 → 出了點問題，請稍後再試
- 網路連線失敗，請檢查您的網路狀態 → 連不上網路，請檢查連線
- 此時段已被其他人預約 → 這個時段已有人預約，請改選其他時段

**確認對話**

- 您確定要刪除此筆訂單嗎？此操作無法復原 → 刪除這筆訂單？刪除後無法復原
- 是否確定要提交本梯次班表？ → 送出這梯班表？

**狀態／系統訊息**（心法 6、7 與一致性規則 5、6 的實例）

- 王小明沒有提交 08/12 的早時段，這段不能排。已改派給 陳大同 → 無法派給指定業務王小明，已自動改派給陳大同
- 陳大同那個時段接不了，已改派給 陳業務 → 原指派業務陳大同無法支援，已自動改派給陳業務
- 陳大同那個時段接不了，這張單已退回未派工行程 → 原指派業務陳大同無法支援，此預約為未派工狀態
- 沒有可指派的業務——7 位服務區不涵蓋台南市東區、1 位當日未提交該時段 → 無人可派發，此預約為未派工狀態
- （原本沒有這句）→ 已自動派發給陳大同　←　系統自己做的事，成功也要說

**通知／狀態**

- 您的訂單已成功建立完成 → 訂單已建立
- 派工已指派給您，請前往查看 → 有新的派工，請點開查看
- 班表提交窗口即將於今日截止 → 班表今天截止，請記得送出
- 付款已成功處理完畢 → 付款完成

**表單提示／placeholder**

- 請輸入您的聯絡電話號碼 → 聯絡電話
- 請於下方欄位填寫備註事項（選填） → 備註（選填）

## 維護（只在案主明確要求時更新，不自動）

**預設不要自動回填 skill。** 平常照這份寫、幫案主改文字就好；即使看到可以通用的原則，也**不主動**改 skill。

只有當案主在某個 session **明確表示**要把這次的修正沉澱回 skill（例如「這個 session 的修正沉澱回 skill」或等義指示）時，才動手更新，並照下面歸位：

- **通用寫作原則**（改「怎麼說」——語氣、精簡、白話、標點、盤古之白等）→ 補進〈核心心法〉／〈標點與排版〉，範例補進〈逐句範例庫〉。
- **產品用語決定**（改了某個詞、或定下新的統一用語）→ 補進〈術語表〉並回寫其他用到的畫面。
- **純系統邏輯或 domain 事實**（不影響「怎麼講」，只是講清楚系統裡什麼是真的）→ **不進 skill**，頂多進 `docs/SPEC.md` 或記憶。

更新完在回覆裡用一句話說明改了什麼。這份是活文件，但由案主決定何時沉澱（與 `ui-design` 同一套非自動迭代做法）。相關：通用 UI/UX 準則見 `ui-design`。
