# UI 設計檢查（通用 · 及格門檻）

這是一份**通用、可跨專案**的 UI/UX 基本準則。目標是「**及格**」——讓第一版設計就沒有明顯毛病，
不是追求完美，也不要在 UI 上耗過多時間。國際通用慣例的濃縮（Nielsen 十大可用性啟發、
Apple HIG／Material 的常識、Refactoring UI 的實務）。

**邊界（本 skill 不管的）：**
- **文案／用字** → 用 `ux-writing` skill（怎麼「說」）。
- **某專案專屬的具體選擇**（人工定的色票 hex、特定共用元件名、術語）→ 在該專案的「設計語言」
  （本 repo：`AGENTS.md` 後台 UX 契約 + `ux-writing` 術語表）。本 skill 只說「**要有**一套語意色、
  別各畫面亂配」；具體「是哪幾個色」看專案設計語言。

## 何時用

- **開任何新畫面/元件、或改動既有 UI 前**：先過〈開工前檢查〉。
- **做完後**：當自我 review 清單再過一次，抓明顯問題。
- 平台不同、原則相同：App 與後台都適用，差別只在元件與尺寸。

> **機制化備忘**：來源專案把「動畫面層檔案前必先啟動本 skill」做成 PreToolUse 閘門
> （寫入畫面層檔案會被擋，直到本 session 啟動過本 skill）。畫面層路徑依專案技術棧而異，
> 模板不帶 hook；專案定型後可由 framework 入口比照落地（列在 sensors-backlog 的精神：能機制化就不要靠自律）。

## 開工前檢查（一頁快篩）

- [ ] **一個畫面一個主目的**，標題講清楚這頁在幹嘛；相關資訊群組在一起、別太擠。
- [ ] **主要動作明顯、好找、好按**：不要逼使用者捲到底才找到；一頁以一個主要按鈕為主，次要動作弱化。
- [ ] **四種狀態都想過**：正常、**載入中**、**空**、**錯誤**——每種都有對應畫面，不要只做「有資料且成功」那種。
- [ ] **每個操作都有回饋**：成功/失敗/處理中要讓人知道；送出中要 disable 按鈕、避免重複送出。
- [ ] **只在有效時才能送出**：必填沒填/格式錯/根本沒改，就 disable 或擋下並說原因。
- [ ] **一致性**：同功能長一樣、放同位置、用**共用元件**；同語意用同一套顏色/圖示/字。
      要加輸入欄位前先問「站上已經有這種欄位了嗎」，有就沿用、不要另造。
- [ ] **視覺基本盤**：文字對比看得清、手機點擊目標夠大（約 44×44pt）、**不要只靠顏色分辨**（配文字或圖示）。
- [ ] **克制**：不加沒必要的說明字、不炫技，預設乾淨。

## Patterns（原則＋Do / Don't）

### 1. 佈局與層次
- 一頁一個主目的；最重要的資訊/動作放在最先看到的地方。
- 相關的東西靠在一起、不相關的用留白/分隔隔開（親近性）。
- Don't：把資料庫欄位原樣一長排堆出來、要使用者自己找重點。

### 2. 主要動作
- 主要動作要**顯眼且觸手可及**。長內容/表單時，把主鈕**固定在畫面底部（sticky）**，不要逼人捲到底。
- 一個畫面**以一個主要按鈕為主**；次要/取消用較弱的樣式（外框/文字鈕）。
- 按鈕用**動詞**、講清楚會發生什麼（「送出申請」而非「確定」）。
- 危險/不可逆動作（刪除、送出後不能改）→ 要**二次確認**。
- Don't：兩三顆都長得像主鈕；主鈕藏在捲動最底。

### 3. 狀態與回饋
- **四態必備**：正常 / 載入中（spinner 或骨架）/ 空（給一句說明＋下一步）/ 錯誤（說發生什麼＋怎麼辦）。
- 每個操作**即時回饋**：成功給提示、失敗給原因、非同步進行中鎖住觸發點。
- 不能按的元件要**看得出來不能按**（灰掉/降透明），最好能讓人知道為什麼。
- **狀態用「顏色＋文字」雙重表示**（色盲/列印也讀得懂）；顏色照專案的語意色系，別畫面各配各的。
- Don't：按了沒反應、重複點會送出多次、只用紅/綠圓點不配文字。

### 4. 表單與輸入
- 送出鍵**只有在可以送出時才可按**（必填齊、格式對、且**真的有改動**）。
- 錯誤**就地顯示**在該欄位旁，說清楚怎麼修；不要只跳一個籠統錯誤。
- 破壞性或大表單：考慮「檢視 / 編輯」分離（預設唯讀，按「編輯」才可改）——降低誤觸、也讓頁面不像「一進來就要你存檔」。
- Don't：全部必填卻不標示；送出後才一次噴一堆錯。

### 5. 一致性
- 同一種東西**長一樣、放一樣的位置**：用**共用元件**（按鈕、徽章、卡片、輸入框），不要每頁各刻一份。
- 同語意共用一套**顏色 / 圖示 / 字詞**（字詞交給 ux-writing 術語表）。
- 位置慣例固定（例：主要動作在底、編輯入口在右上），跨頁不要亂跳。
- **同一種資料型別只用一種輸入元件**（日期、時間、金額、電話…）。要加額外行為就**包在共用元件外面**
  （繼承／包一層殼），不要為了多一個小功能另造一個。
- **慎用瀏覽器原生控制項**（如 `<input type="date">`）：外觀、格式、語言由**使用者的瀏覽器與作業系統**
  決定，站方控制不了，很容易和站上其他欄位長得不一樣。要嘛全站都用原生、要嘛全站都用自訂，不要混用。
- **日期/時間格式跟隨在地慣例**且全站一致（哪一種格式屬專案設計語言，見該專案的設計語言文件）。
- **快捷鍵克制**：只留真正常用的（日期通常只需要「今天」）。選項越多，使用者辨識成本越高。
- Don't：這頁藍色代表成功、那頁藍色代表進行中；這頁日期是原生選擇器、那頁是自訂日曆。

### 6. 視覺基本盤（及格即可，低成本三項）
- **對比**：正文文字與背景對比足夠（別用太淺的灰字當內文）。
- **點擊目標**：手機可點區域約 44×44pt 以上，別做太小太密。
- **不只靠顏色**：狀態/區別一律「顏色＋文字或圖示」。
- 有支援深色模式/RWD 就**別破版**（沒支援就不勉強）。
- 這層只做到「不明顯難用」即可，不追求完整無障礙規範。

### 7. 克制
- 預設乾淨：**不主動加說明/提醒文字**，沒必要就不加（要加先想清楚）。
- 不為了炫而炫；動效、漸層、陰影點到為止。

## 維護（重要：只在案主明確要求時才動）

**與 `ux-writing` 不同**：本 skill **不自動回填**。即使案主在對話中提了通用 UI 要求，也**先不要**改 skill。

- **只有**當案主**口頭明確說**類似「OK，我們來 review 這個對話串，討論一下有沒有值得加進（ui-design）skill 的地方」時，才啟動：
  1. 回顧該對話串，挑出案主提過的**通用**（可跨專案）UI 要求/更正。
  2. 分辨哪些是「通用原則」（→ 可進本 skill）vs「本專案主觀決定」（→ 進專案設計語言，不進本 skill）。
  3. 跟案主討論確認後，才更新 skill；框架變更記得 bump 版號＋補 `docs/FRAMEWORK.md`。
- 平時就**照現有清單套用**、不擅自擴充。
